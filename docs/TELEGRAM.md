# 가상 Go1 텔레그램 보고

기존 Hermes 봇과 기본 대화방을 사용해 시설 점검 시뮬레이션 정보를 전달합니다. 텔레그램의 실제 발신 계정은 Hermes 봇이며, 메시지 본문에는 `가상 Go1 R-01`이 보고자로 표시됩니다.

## 사용 순서

1. 웹 서버와 브리지를 실행합니다: `npm run dev`, 별도 터미널에서 `npm run agent:bridge`.
2. `http://localhost:5180/`을 열고 상단 **텔레그램**을 누릅니다.
3. **전송 준비됨** 표시와 받는 봇·대화방을 확인합니다.
4. **연결 테스트** 또는 **현재 상태 보내기**를 눌러 메시지를 보냅니다.
5. **임무 진행 자동 보고**를 켠 뒤 시나리오를 실행하면 이후 주요 이벤트를 보고합니다.
6. 임무 종료 후 보고 종류를 **대응 요약**으로 바꾸고 전송합니다.

자동 보고는 페이지를 열 때마다 꺼져 있습니다. 실행 중에 켜면 이전 이벤트를 다시 보내지 않습니다. 끄면 아직 요청하지 않은 자동 보고를 비우며, 이미 요청한 메시지는 전송될 수 있습니다. 브라우저가 닫히면 이후 시뮬레이션 이벤트를 보고하지 않습니다. 여러 탭에서 동시에 자동 보고를 켜면 각 탭의 임무가 별도로 보고되므로 발표에는 한 탭을 사용합니다.

## 가상 설비 사진까지 받기

스마트폰 점검 명령에는 촬영이 포함됩니다. **스마트폰 명령 받기**를 켠 뒤 기존 Hermes 대화방에서 `고원아, 냉각 설비 점검해줘` 또는 `고원아, 냉각 설비 점검하고 사진 보내줘`라고 음성·텍스트로 지시합니다.

Go1이 장비 앞에 도착해 관측 판정을 마치면 해당 위치의 3D 카메라로 장비를 촬영합니다. JPEG 사진에 설비 ID·이름, 온도 센서·열화상 관측·관측 차이, 판정, KST 촬영 시각, 실행 ID와 촬영 위치를 기록합니다. **가상 점검 이미지 / 합성 관측** 표시를 포함하며 실제 CCTV나 로봇 카메라 사진으로 설명하지 않습니다. 장비 조치를 수행하지 않는 기존 점검·보고·복귀 흐름을 유지합니다.

웹의 **현장 점검 보고**에도 같은 사진을 표시하며 **사진 저장**으로 내려받을 수 있습니다. 웹에서 직접 시작한 점검은 사진 미리보기·저장을 제공하고, 스마트폰에서 시작한 점검은 기존 Hermes 대화방으로 사진을 자동 전송합니다. 사진 전송은 **임무 진행 자동 보고** 스위치와 독립적으로 동작합니다.

- 현장 관측을 완료한 실행마다 사진 한 장만 촬영·전송합니다. 정상·과열·센서 불일치 판정을 사진에 반영합니다.
- 도착 전 복귀하거나 점검이 중단되어 관측 판정이 없으면 사진을 만들거나 전송하지 않습니다.
- 사진 전송을 기다리는 동안에도 브라우저는 명령 수신을 계속합니다. 전송 실패는 사진 상태와 텔레그램 기록에 표시하며, 결과가 불확실한 사진은 자동 재전송하지 않습니다.
- 사진은 브라우저 메모리에서 생성하고 로컬 브리지로 전달합니다. 브리지는 고정된 Hermes 수신 대화방에 [sendPhoto](https://core.telegram.org/bots/api#sendphoto)의 multipart 파일 업로드로 보냅니다. 토큰과 수신 대화방을 사진 요청에 넣거나 브라우저에 공개하지 않습니다.

사진 기능이 없는 옛 브리지가 실행 중이면 해당 브리지를 재시작하고 웹을 새로고침합니다. 공개 GitHub 데모에서는 웹 촬영·저장만 가능하며 실제 텔레그램 발송에는 노트북의 localhost 브리지가 필요합니다.

## 스마트폰에서 Go1에게 지시

웹의 **Go1 자율 점검**으로 시작한 임무도 **임무 진행 자동 보고**를 켜면 같은 Hermes 대화방으로 보고합니다. 정상 판정에서는 자동 복귀하고, 이상 판정에서는 현장 보고 후 웹의 **보고 확인 · 복귀 지시**를 기다립니다. 스마트폰에서 접수한 점검은 결과를 보고한 뒤 복귀하는 기존 흐름을 사용합니다. 웹 보고 화면은 텔레그램 연결과 별개로 사용할 수 있습니다.

기존 Hermes의 텔레그램 수신기에 `facility-go1` 확장을 추가합니다. 이 PC에는 설치와 기본 Hermes gateway 재시작을 완료했습니다. 다른 PC에서 설정할 때는 다음 순서로 실행합니다.

```powershell
.\Install-Hermes-Go1.ps1
hermes gateway restart
```

1. 웹의 Go1 정밀 모드 또는 경량 모드를 준비합니다.
2. 텔레그램 패널의 **점검 환경**을 선택합니다. `CH-02 과열 예시`, `CH-02 센서 오류 예시`, `정상 장비 예시`, `현재 모델 상태`를 지원합니다. 예시 환경은 CH-02의 합성 관측 초기값을 설정하며 다른 장비는 정상 온도 예시를 사용합니다.
3. **스마트폰 명령 받기**를 켜고 노트북의 웹 화면을 열어둡니다.
4. 스마트폰의 기존 Hermes 봇 대화방에서 아래처럼 보냅니다.

| 명령 | Go1의 동작 |
|---|---|
| `Go1 CH-02 점검해줘` | 냉각 설비로 이동해 관측·판정·보고·복귀 |
| `Go1 공조 유닛 점검해줘` | AHU-01 점검 위치로 이동 |
| `Go1 탱크 점검해줘` | TK-01 점검 |
| `Go1 펌프 점검해줘` | PU-01 점검 |
| `Go1 배전반 점검해줘` | EL-01 점검 |
| `Go1 문제 있는 장비 점검해줘` | 이 MVP의 이상 예시 대상인 CH-02 점검 |
| `Go1 상태` | 현재 위치·온도·연결·배터리 보고 |
| `Go1 정지` | 웹 Go1의 실행 중지, 확인된 정지 상태 보고 |
| `Go1 복귀` 또는 `Go1 복귀해줘` | 웹·스마트폰 점검 중 현재 위치에서 도킹 위치로 복귀 |
| `Go1 돌아와` 또는 `/go1 return` | 같은 복귀 명령 |

웹에서 시작한 점검도 **스마트폰 명령 받기**가 켜져 있으면 `Go1 복귀`로 돌아오게 할 수 있습니다. 현장 보고 후의 이상 판정은 유지합니다. 이동 중 복귀로 점검을 중단하면 **현장 점검 미완료 / 이상 유무 미확인**으로 보고합니다. 명령 접수, 웹에서 확인된 복귀 지시 반영, 실제 도킹 완료를 구분해 텔레그램으로 보냅니다. 이미 복귀 중이거나 도킹을 마친 경우 현재 상태만 안내합니다.

`Go1 정지` 또는 일시정지로 멈춘 점검도 연결·충전 상태가 정상이면 `Go1 복귀`로 돌아올 수 있습니다. 물리 실행 오류는 웹에서 초기화해야 합니다. 연결 단절·배터리 부족 상태에서 보류한 복귀 명령은 나중에 자동 실행하지 않으며 상태 복구 후 다시 지시합니다.

`/go1 inspect CH-02`, `/go1 status`, `/go1 stop` 형태도 지원합니다. Go1 또는 고원으로 시작하는 명령은 정해진 문법과 허용 장비로 해석하며 별도 LLM 호출이 필요하지 않습니다. 일반 Hermes 대화는 기존 흐름으로 처리됩니다.

## 음성으로 고원에게 지시

이 PC에는 `faster-whisper`와 한국어 로컬 STT, 음성 수신 확장을 설치하고 기본 gateway를 재시작했습니다. 노트북 웹의 **스마트폰 명령 받기**를 켠 뒤 기존 Hermes 봇 대화방에서 마이크를 눌러 **음성 메시지**를 보냅니다.

| 말할 문장 | 동작 |
|---|---|
| 고원아, 냉각 설비 점검해줘 | CH-02 이동·관측·판정·보고·복귀 |
| 고원아, 공조 유닛 점검해줘 | AHU-01 점검 |
| 고원아, 탱크 점검해줘 | TK-01 점검 |
| 고원아, 상태 알려줘 | 현재 상태 보고 |
| 고원아, 정지해줘 | 실행 중지 |
| 고원아, 복귀해줘 | 진행 중인 점검에서 도킹 위치로 복귀 |

**음성 메시지 → Hermes 한국어 STT → 인식 문장 표시 → 고원/고원아를 Go1으로 정규화 → 허용 명령 확인 → 웹 동작·보고** 순서입니다. “고원아. 복귀해 줘.”처럼 STT가 붙인 마침표와 띄어쓰기도 처리합니다. 명령 하나씩 짧게 말합니다. 음성을 인식하지 못하면 실행하지 않고 다시 말해달라는 안내를 보냅니다. 인식 결과가 다른 장비로 나왔으면 `고원아, 정지해줘` 또는 웹의 일시정지를 사용합니다.

일반 음성 대화는 같은 Hermes 수신 흐름으로 돌려보내며 재인식·중복 인식 문장 전송을 피합니다. 음성 수신은 기존 봇이 담당하고 새 `getUpdates` 폴링이나 webhook을 만들지 않습니다. mp3 같은 **오디오 파일 첨부**는 Hermes의 일반 파일 처리와 구분되므로 Telegram의 마이크로 녹음한 음성 메시지를 사용합니다.

다른 Windows PC에서는 다음과 같이 설정합니다.

```powershell
.\Install-Hermes-Go1.ps1 -Voice
hermes gateway restart
```

설치기는 해당 Hermes의 Python 가상환경에 `faster-whisper`를 설치하고, `config.yaml`의 STT를 `provider: local`, `language: ko`, `local.model: base`, CPU int8, 인식 문장 표시로 설정합니다. 설비 이름과 고원을 초기 어휘 힌트로 전달합니다. 원본 설정은 Hermes 홈의 `config.before-go1-voice-*.yaml`에 백업합니다. 기본 프로필만 적용하며 다른 프로필의 gateway는 재시작하지 않습니다. 모델 파일은 첫 사용 시 다운로드하고 이후 인식은 PC에서 수행합니다. Telegram 송수신에는 인터넷이 필요합니다.

`base`의 인식 품질이 부족하면 `.\Install-Hermes-Go1.ps1 -Voice -WhisperModel small`로 바꾸고 gateway를 재시작할 수 있습니다. `small`은 다운로드·메모리·연산량이 더 큽니다. 학교 Ubuntu Hermes에서도 같은 플러그인을 사용할 수 있지만 `BRIDGE`의 loopback 주소는 그 Hermes가 실행되는 호스트를 뜻합니다. 학교에서 STT를 하려면 노트북 브리지까지의 인증된 중계 연결을 별도로 구성해야 합니다.

점검 접수, 현장 판정, 복귀 결과를 기존 대화방으로 자동 전송합니다. **임무 진행 자동 보고**를 따로 켤 필요는 없습니다. 판정은 센서·열화상의 60°C 경보 기준과 5°C 차이 기준으로 `정상 범위`, `과열 의심`, `센서 불일치`, `추가 점검 필요`를 구분합니다. 이는 예시 관측 기준이며 고장 원인이나 산업 안전의 확정 진단이 아닙니다. 원격 점검은 환기 설정을 변경하지 않습니다.

같은 수신 메시지는 `.runtime/go1-inbox.json`에 해시와 작업 ID로 기록해 브리지 재시작 후에도 재출동하지 않습니다. 한 웹 화면만 스마트폰 명령을 받습니다. 웹 연결이 없거나 다른 임무가 실행 중이면 출동을 보류하고 안내를 보냅니다. 화면을 닫거나 백그라운드로 전환하면 원격 임무를 계속 실행하지 않으며 완료를 확인하지 못한 경우 안내합니다. 정지·보류한 임무는 웹에서 현재 상태를 확인하고 초기화 또는 재개합니다.

기본 개인 대화방은 해당 대화방의 사용자만 지시할 수 있습니다. 그룹에서는 Hermes의 허용 사용자와 서버의 기본 대화방·토픽이 일치해야 합니다. 프로젝트 전용 그룹 설정을 사용할 때는 `TWIN_TELEGRAM_ALLOWED_USERS`에 허용 사용자 숫자 ID 목록을 지정합니다. 봇 토큰이나 임의 명령·수신자를 웹에 전달하지 않습니다.

현재 상태에는 위치, 모델·센서·열화상 온도, 배터리·연결, 속도·환기와 제어 모드가 포함됩니다. 대응 요약은 현재 runId의 판단, 검증·복귀 결과, 시뮬레이션 시간, 거리, 경로 변경·정지 및 정책 추론 횟수를 추가합니다. 자동 보고에는 Agent의 분류·로컬 CLI 판단과 환기 조치도 포함됩니다. 진행 중에도 요약을 보낼 수 있으며 결과는 `대응 진행 중`으로 표시됩니다. 모든 보고는 합성 관측과 시뮬레이션 기록임을 명시합니다.

## 기본 설정

서버는 `HERMES_HOME` 환경 변수가 가리키는 폴더의 `.env`에서 다음 값을 읽습니다.

```text
TELEGRAM_BOT_TOKEN
TELEGRAM_HOME_CHANNEL
TELEGRAM_HOME_CHANNEL_THREAD_ID  (토픽을 사용할 때만)
```

`HERMES_HOME`을 지정하지 않은 Windows에서는 `%LOCALAPPDATA%\hermes`, 다른 운영체제에서는 `~/.hermes`를 사용합니다. 브리지는 기존 봇 설정을 읽어 재사용합니다. `-Voice` 설치기를 실행할 때만 해당 홈의 STT 설정을 백업하고 변경합니다.

전용 봇이나 다른 대화방을 사용할 때만 저장소의 `.env.example`을 `.env.local`로 복사해 아래 두 값을 함께 설정합니다. 변경 후 브리지를 재시작합니다.

```text
TWIN_TELEGRAM_BOT_TOKEN=자신의_봇_토큰
TWIN_TELEGRAM_CHAT_ID=대화방_ID
TWIN_TELEGRAM_THREAD_ID=
```

브리지 실행 터미널의 환경 변수가 파일 설정보다 우선합니다. 받는 대화방은 숫자 ID로 설정합니다. `.env.local`과 실제 토큰은 Git에서 제외되며, 브라우저에는 봇 이름·대화방 이름과 ID 마지막 네 자리만 표시됩니다.

## 전송 결과와 문제 해결

- **전송됨**: Telegram이 메시지 ID와 지정 대화방의 발송 응답을 반환했습니다. 사용자의 열람 여부를 의미하지는 않습니다.
- **확인 필요**: API 오류 또는 네트워크 단절로 결과가 확정되지 않았습니다. 자동 보고를 중지하며, 대화방을 확인한 뒤 직접 다시 전송할 수 있습니다. 중복을 피하기 위해 자동 재시도하지 않습니다.
- **연결 필요**: 브리지, 인터넷 연결 또는 서버의 봇·대화방 설정을 확인합니다. 기존 봇과 먼저 대화를 시작해야 개인 대화방으로 보낼 수 있습니다.
- 코드 업데이트 후 옛 브리지가 실행 중이면 해당 브리지를 종료하고 다시 시작합니다. 실행기가 시작한 브리지는 `Stop-Demo.ps1`로 종료할 수 있습니다. 이미 실행 중인 브리지에 `npm run agent:bridge`를 다시 입력하면 기존 프로세스를 재사용합니다.

브리지는 보고를 순차 처리하고 발송 시도 사이에 최소 3.2초를 둡니다. 같은 프로세스의 최근 전송 ID를 기억해 중복 요청을 억제합니다. 기존 Hermes의 독립적인 발송까지 제한하는 것은 아니므로 공유 봇의 사용량에 따라 Telegram 제한 오류가 발생할 수 있습니다. 이 동작은 [Telegram 전송 제한 안내](https://core.telegram.org/bots/faq#my-bot-is-hitting-limits-how-do-i-avoid-this)를 참고했습니다.

실제 발송과 명령 실행은 localhost에서만 사용할 수 있습니다. GitHub Pages 또는 LAN 주소에서는 보고·가상 사진 미리보기를 제공합니다. 텍스트는 [sendMessage](https://core.telegram.org/bots/api#sendmessage), 점검 사진은 [sendPhoto](https://core.telegram.org/bots/api#sendphoto)로 발송하고 [getChat](https://core.telegram.org/bots/api#getchat)으로 지정 대화방을 확인합니다. 수신은 기존 Hermes gateway가 담당합니다. 브리지는 별도의 webhook이나 getUpdates 폴링을 등록하지 않습니다.
