# 로컬·학교 PC Agent 연결 설계

## 지금 구현된 연결

노트북 브라우저 → Vite /agent 프록시 → localhost Node 브리지 → 설치된 Codex 또는 Hermes → 구조화된 점검 계획 → 관측·제약 검증 → 브라우저 시뮬레이션.

기존 CLI의 로그인과 모델 설정을 사용합니다. 사용자 계정 설정이나 텔레그램 구성을 변경하지 않습니다. 최초 분류만 모델이 맡고, 도구 실행과 임무 상태 전이는 결정적인 코드가 담당합니다. 자유로운 대화형 모델이 설비나 셸을 직접 제어하는 구조로 확장하지 않았습니다.

입력은 runId, 고정된 CH-02 대상, 센서·열화상 값, 기준 온도, 배터리, 연결 상태와 제약입니다. 출력은 action, target, reason입니다. action은 inspect_heat / inspect_sensor / hold_low_battery 중 하나입니다. 임의 명령 필드는 거부합니다.

CLI 대기 동안 시뮬레이션 시간을 멈추므로 발표에서 모델 응답 지연이 열모델 결과에 영향을 주지 않습니다. 이 시간 정지는 시연 편의 기능입니다. 실제 설비의 로컬 안전 제어는 상위 Agent 응답 지연과 독립적으로 동작해야 합니다.

## 학교 Ubuntu·Docker를 사용하는 다음 단계

이 작업에서는 원격 접속이나 Docker 구성을 변경하지 않았습니다. 연결 정보가 확보되면 아래 방식으로 확장할 수 있습니다.

1. 학교 PC 컨테이너 안에서 동일한 브리지 프로토콜과 CLI 실행기를 제공합니다. 브리지는 서버의 loopback에 바인딩합니다.
2. 노트북에서 SSH 로컬 포트 포워딩으로 브리지에 접근합니다. 공개 인터넷에 CLI 실행 엔드포인트를 노출하지 않습니다.
3. 플랫폼과 설치 경로에 맞춰 CODEX_CLI_PATH / HERMES_CLI_PATH / HERMES_AGENT_ROOT / HERMES_PYTHON_PATH를 설정합니다. Hermes 내부 모듈을 사용하는 Python 어댑터는 해당 버전에서 확인합니다.
4. 현재 프런트엔드는 같은 /agent 프로토콜을 사용하므로 로컬 브리지 대신 포워딩된 브리지를 Vite 프록시 대상으로 지정할 수 있습니다.

실제 구성에는 SSH 호스트·계정·인증 방식, 컨테이너 이름, CLI 설치 경로와 로그인 상태가 필요합니다. 이 정보를 소스 저장소에 저장하지 않습니다.

## 구현된 텔레그램 보고

브라우저 관측·실행 기록 → 로컬 Node 브리지 → 기존 Hermes 봇 → Hermes 기본 대화방으로 가상 Go1의 상태와 대응 요약을 실제 발송합니다. 웹에서 자동 보고를 켜면 이후 임무의 경보·Agent 판단, 현장 점검·환기 조치, 정지·복구와 복귀 이벤트를 순차 전송합니다.

보고마다 같은 runId를 사용합니다. 같은 전송 ID는 브리지 프로세스 안에서 중복 처리하고, 받는 대화방은 서버 설정으로 고정합니다. 토큰은 Hermes 설정 파일에서 읽어 서버 내부에서만 사용합니다. Hermes의 수신 메시지를 가져오거나 봇 설정을 변경하지 않습니다. [텔레그램 사용 방법](TELEGRAM.md)에 설정 경로와 동작 범위를 정리했습니다.

스마트폰의 Go1 명령은 Hermes의 `pre_gateway_dispatch` 확장에서 기존 gateway 권한을 확인한 뒤 로컬 브리지로 전달합니다. 브리지도 기본 대화방·사용자·토픽을 확인하고, 허용한 장비 점검·상태·정지로 변환합니다. 한 웹 화면이 임무를 실행하고 같은 jobId·runId로 관측 및 복귀 결과를 보고합니다. 별도의 getUpdates 폴링이나 webhook을 등록하지 않습니다.

원격 점검은 시설 대응 시나리오와 별도로 이동·관측·판정·보고·복귀를 수행합니다. 환기 조치를 실행하지 않으며 배터리·통신·장애물 제약을 유지합니다. 현재 노트북 화면이 실행 주체이므로 브라우저가 닫힌 상태의 상시 운영은 지원하지 않습니다. 상시 운영에는 향후 서버의 시뮬레이션·로봇 실행기와 내구성 있는 작업 큐가 필요합니다.

## 연구를 추가하는 위치

브라우저 환경·사고 상태 전이와 학습 정책을 분리했습니다. 향후 초파리 뇌 기반 감각 통합 모델 또는 강화학습 내비게이션 정책은 같은 관측·명령 인터페이스에서 평가하도록 추가합니다.

평가에서는 관측 입력, 제어 주기, 계산 예산, 장애물·센서 잡음 조건, 성공 판정과 실패 정지를 동일하게 맞춥니다. 완료율, 충돌, 불필요한 출동, 정지·복구, 에너지·시간을 반복 실험으로 비교합니다. 현재 공개 Go1 보행 정책은 이 연구 정책의 성과로 간주하지 않습니다.
